## Architecture boundary

The Phase 1 architecture proposes a static React frontend on the KASIB Cloudflare Worker `ibuka-poc` (static assets, Workers Builds) and Supabase Auth/Data API. The browser is untrusted. A frontend build may contain only a public Supabase URL and publishable key, never the service-role key, database password, SMTP credential or provider token. The database must enforce company ownership with grants and row-level security; hiding another company's ID in the UI is not access control. The client confirms `ibuka.co.ke` is already a Custom Domain on the `ibuka-poc` Worker and the Cloudflare zone is Active; main `83c62d5` was deployed and observed live on that domain on 24 September 2026 (the pending demo branch with the public `wrangler.jsonc` vars and the Vite bridge has not yet deployed), and the email sender is not yet selected.

The proposed data model and access contract were documented before implementation. When code exists, update this guide to point to the exact entry points, environment template, build/test commands, deployment workflow and migration revision. Keep a clear distinction between **proposed**, **implemented**, **tested** and **client-approved** behavior.

## Working on a change

1. Read the current task and the source/version it depends on. Use a dedicated linked Git worktree for the ticket.
2. State the observable acceptance check before editing. Change one behavior at a time and explain the source-to-UI-to-data path so a new contributor can follow it.
3. Use synthetic company/tester data until data-location and test-data rules are approved. Keep credentials in the KASIB provider settings or local ignored environment files; commit only an example template with placeholders.
4. Run the relevant build/tests and inspect the actual staging state before claiming a deployment works. For a company-scoped feature, exercise two independent test companies and signed-out access at the real API boundary.
5. Record the revision, sample-data version, test evidence and any remaining client decision in the handover notes. Update this file whenever the actual architecture or commands change.

For a newcomer such as Albie, trace one item end to end: **source clause → Trevor's field/prompt ID → UI input → saved value → derived status or score → acceptance check**. The typed input, completion status, and regulatory conclusion are different things. Ask which one a number represents before changing the calculation.

## Worker build repair (B05, 24 September 2026)

The staging host is the client-created Cloudflare Worker `ibuka-poc` with Workers Builds, not Cloudflare Pages. On commit `f0ae346`, Workers Builds ran `npx wrangler deploy` with no committed Wrangler config and no separately executed build step; Wrangler's automatic framework setup detected Vite 5.4.21 and stopped, demanding Vite ≥ 6.0.0. This revision commits `wrangler.jsonc` (`name: ibuka-poc`, `compatibility_date: 2026-09-24`, `assets.directory: ./dist`, `keep_vars: true`, `routes: [{ "pattern": "ibuka.co.ke", "custom_domain": true }]`; no script, path routes, vars or secrets), which prevents automatic framework setup so the Vite 5 output deploys as plain static assets. `keep_vars: true` stops a Wrangler deploy from deleting the existing Worker's dashboard-configured plain variables (a deploy is otherwise the source of truth for those; encrypted secrets are never deleted by a deploy); this protects variables we cannot inspect while signed out. The Custom Domain is managed as code: the pattern is the exact hostname with no path (a Custom Domain matches all paths of that hostname; `www.` would be a separate hostname), the client confirms the domain is already attached on the Worker and the zone is Active, and Cloudflare syncs the declared Custom Domain at deploy; the `*.workers.dev` URL state is not asserted by this config (neither enabled nor disabled) and no such URL is claimed. The Cloudflare deploy and live page were verified on 24 September 2026 (see the status below). Workers Builds does not honor build commands from the Wrangler config and the route is not a way to set the build command, so the dashboard build command `npm run build` (deploy `npx wrangler deploy`, both user-confirmed by screenshot) plus the public `VITE_` build variables still govern builds. No app code, dependencies or visuals changed. Status: **implemented, deployed and observed live.** The build of main `83c62d5` succeeded in Cloudflare Workers Builds on 24 September 2026, and `https://ibuka.co.ke/` served the Daraja page (title plus JS/CSS assets over HTTPS 200). Client approval of the deployment is not inferred from the successful deploy.

Contrast was verified by WCAG relative-luminance calculation: red accent text on paper 4.92:1, near-white button label on red 5.06:1, and the button hover fill at an opaque darkened `#b52b31` 5.90:1 (all AA, >= 4.5:1); gold measures ~1.95:1 on paper and is decorative only, never carrying text. The vendored shadcn Button hover style (`hover:bg-primary/80`, which composites to 3.77:1) is overridden for the default variant by a narrowly scoped, deliberately **unlayered** rule in `src/index.css` — unlayered author styles outrank the utilities cascade layer, where a `@layer components` override would lose because layer order outranks specificity. The vendored component itself is untouched.

## Public Supabase config as code (24 September 2026, branch task/demo-review-preview)

The two **public** values (`VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`) are now versioned as `vars` in `wrangler.jsonc` — the repo JSON is their source of truth instead of the Cloudflare dashboard. They are the publishable pair only; the service-role key, database password, SMTP credentials and provider tokens remain forbidden in the repository (the values match the ignored b04 `.env.local`; no private material was copied). `keep_vars: true`, the exact-hostname `ibuka.co.ke` Custom Domain route and the static-assets settings are unchanged; `wrangler.jsonc` stays strict JSON (no comments/trailing commas) so both Wrangler and the Vite bridge can parse it.

Mechanism and precedence: Wrangler `vars` are **runtime** Worker config and are not available to the Vite build, so a minimal `vite.config.ts` bridge (`loadEnv` + `process.env`, no new dependency) resolves each value as process env (Cloudflare **Build variables**, now optional overrides) → Vite `.env` files (e.g. ignored `.env.local`) → `wrangler.jsonc` default, and assigns it into `process.env` before the build so Vite embeds it. This works in Cloudflare's existing `npm run build` → `npx wrangler deploy` sequence. Dashboard **Runtime** variables are inert here (static-assets-only Worker, no script). A missing or unreadable value never breaks the build; the page reports "Not configured" honestly. `src/config.ts` validation and the read-only diagnostic are unchanged. The values are not duplicated into `.env.production`, app source constants, GitHub secrets or anywhere else.

Status: **implemented and locally tested (clean build without env/.env files embeds the JSON values; process-env overrides win; calculator tests still pass); not yet deployed or client-approved.**
